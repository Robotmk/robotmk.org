# FAQ Page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a bilingual (DE/EN) FAQ page at `/de/faq/` and `/en/faq/` that groups 22 recurring questions into five categories, shows answers in collapsible panels, supports category pills plus live search, and appends a discreet Clarity Call link to every answer.

**Architecture:** Follows the established page pattern of this repo exactly — all copy lives in `data/<lang>/faq.yaml`, `content/faq/_index.<lang>.md` carries only front matter, and `layouts/faq/list.html` renders the page. Answers use native `<details>`/`<summary>` so the page is fully usable without JavaScript; `assets/js/faq.js` is a progressive enhancement that reveals the search/pill controls and toggles the `hidden` attribute on non-matching items.

**Tech Stack:** Hugo v0.124.1 extended, Go templates, YAML data files, plain ES modules bundled via `js.Build` from `assets/js/main.js`, plain CSS concatenated in `layouts/partials/head/css.html`.

## Global Constraints

- **Design tokens only.** Never hardcode colors, spacing or font sizes. Use the custom properties in `assets/css/tokens.css` (`--color-*`, `--space-*`, `--text-*`, `--font-*`).
- **Sharp corners.** `--radius: 0px` — the design system uses no rounded corners. Pills, inputs and panels are square. Do not add `border-radius`.
- **Booking URL comes from config.** Every booking link uses `.Site.Params.booking_url` (`https://meet.brevo.com/simon-meggle`) with `target="_blank" rel="noopener"`. Never hardcode the URL in a template or data file.
- **Micro-CTA copy is defined once** in `meta.cta_text` / `meta.cta_link` per language and reused for all 22 answers. Do not repeat it per question.
- **No `docs.google.com` links** in any published answer.
- **No dated claims** ("in spring 2025 …"). Copy must stay true without an edit next year.
- **Both languages stay in sync.** `data/de/faq.yaml` and `data/en/faq.yaml` must contain the same category `id`s in the same order and the same number of questions per category.
- **Verification is build-based.** This repo has no test framework. Every task verifies with `hugo --gc --minify` (must exit 0, no `ERROR`/`WARN` about the FAQ) plus targeted `grep` against the generated files in `public/`.

  - id: concepts
    name: "Grundbegriffe"
    questions:
      - q: "Was ist eine „Suite“?"
        a: |
          Eine Suite ist eine Textdatei mit Robot-Framework-Code, in der ein oder mehrere Tests (auch „Test Cases“ genannt) beschrieben sind. Robotmk führt diese Suites auf den überwachten Hosts aus — unter Windows wie unter Linux.

          Suites dienen in erster Linie dazu, Tests zu gruppieren.

      - q: "Was ist ein „Test“?"
        a: |
          Ein Test ist ein einzelnes **Szenario**, das einen bestimmten Aspekt einer Anwendung prüft.

          Was in einen Test gehört, entscheiden Sie. Sie können 5 Szenarien in einem einzigen Test abbilden — oder 5 Tests mit je einem Szenario.

          Der erste Weg spart Lizenzkosten, packt aber sehr Unterschiedliches in einen einzigen Service. Nur der zweite Weg erlaubt es,

          - einzelne Szenario-Zustände in NagVis darzustellen und
          - für einzelne Tests gezielt bestimmte Teams zu benachrichtigen.

          In der Praxis lohnt sich die feinere Aufteilung fast immer.

      - q: "Was sind Keywords?"
        a: |
          Keywords sind die Bausteine, aus denen Tests bestehen. Sie verhalten sich wie Funktionen in einer Programmiersprache: Sie nehmen Parameter entgegen, können Rückgabewerte liefern und lassen sich beliebig tief ineinander verschachteln.

          Genau diese Verschachtelung macht Robot-Framework-Tests lesbar und langfristig wartbar.

      - q: "Was sind „Test-Services“?"
        a: |
          Der Robotmk-Check auf dem Checkmk-Server wertet die Rohdaten der Robot-Framework-Ausführungen aus und legt für **jeden Test** einen eigenen Service an — den Test-Service.

          Dieser Service zeigt den Zustand des Tests (erfolgreich / fehlgeschlagen) und alarmiert auch bei Laufzeitüberschreitungen.

          Die Summe aller Test-Services innerhalb einer Checkmk-Subscription bestimmt den Umfang für Synthetic Monitoring — sie ist die einzige Größe, die für die Lizenzierung zählt.

  # ── 3 ───────────────────────────────────────────────────────────────────────
  - id: licensing
    name: "Lizenzierung & Kosten"
    questions:
      - q: "Kann ich Synthetic Monitoring ausprobieren?"
        a: |
          Ja. Bis zu drei Test-Services lassen sich in Checkmk ohne Subscription betreiben — genug, um Synthetic Monitoring mit echten Tests in der eigenen Umgebung zu evaluieren.

          Wichtig zu wissen: Dieses Kontingent ist ein **Testangebot, kein Dauerrabatt**. Sobald Sie eine Synthetic-Monitoring-Subscription abschließen, entfallen die drei freien Test-Services. Ab diesem Punkt gilt der Einsatz als produktiv — und jedem produktiv überwachten Test-Service steht ein Gegenwert gegenüber, deshalb zählt dann jeder einzelne in den Umfang Ihrer Subscription.

          Die jeweils gültigen Konditionen finden Sie auf [checkmk.com](https://checkmk.com).

      - q: "Was passiert, wenn ich das Ausführungsintervall einer Suite verkürze?"
        a: |
          Nichts — außer dass Sie eine höhere Auflösung in Ihren Testdaten bekommen.

          Genau an dieser Stelle laufen bei aktionsbasierten Wettbewerbern die Kosten hoch: Dort zahlen Sie pro Testlauf oder pro Aktion. Bei Checkmk bleiben die Kosten konstant, weil ausschließlich die Anzahl der Test-Services zählt.

          Warum das ein so großer Unterschied ist, rechne ich unter [Warum Robotmk](/de/why-robotmk/) im Detail vor.

      - q: "Ich will eine bestehende SM-Lösung ablösen. Wie schätze ich die Kosten ab?"
        a: |
          Dafür brauchen Sie nur zwei Zahlen aus Ihrem Bestandssystem:

          1. die Anzahl der KPIs bzw. Zustände, die es heute liefert, und
          2. die durchschnittliche Laufzeit der zugrunde liegenden Tests.

          Die erste Zahl entspricht grob der Anzahl der Test-Services, die Sie in Checkmk brauchen werden — und damit dem Umfang der Subscription. Mehr ist für eine erste belastbare Abschätzung nicht nötig.

      - q: "Wie entwickelt sich der Preis, wenn ich weitere Standorte hinzunehme?"
        a: |
          Standorte sind für die Lizenzierung keine eigene Größe — genauso wenig wie die Anzahl der Robotmk-Hosts in Checkmk. Sie zahlen weder pro Standort noch pro Host.

          Entscheidend ist ausschließlich die Gesamtzahl der Test-Services innerhalb einer Subscription. Führen Sie dieselbe Suite an mehreren Standorten aus, entstehen dort natürlich jeweils eigene Test-Services — aber der Preis folgt weiterhin dieser einen, gut planbaren Größe.

      - q: "Beeinflusst das Check-Intervall des Checkmk-Agenten den Preis?"
        a: |
          Nein, überhaupt nicht.

          Das Ausführungsintervall der Robot-Framework-Suites ist vollständig unabhängig vom Check-Intervall des Checkmk-Agenten. Der Agent holt lediglich ab, welche Ergebnisse zuletzt vorlagen; wie oft er das tut, hat auf die Lizenzierung keinerlei Einfluss.

      - q: "Sind die Robot-Framework-Libraries schon vor dem Lizenzkauf zugänglich?"
        a: |
          Ja, vollständig. Das Library-Ökosystem von Robot Framework ist Open Source und frei verfügbar — Browser-Automatisierung, SAP, Citrix, REST, Datenbanken und vieles mehr. Sie können sofort loslegen und Tests schreiben, ohne irgendetwas zu kaufen.

          Eine Subscription brauchen Sie erst für **Robotmk** — die Integrationsschicht, die Ihre Robot-Framework-Tests mit Checkmk verbindet. Bis zu drei Test-Services lassen sich zum Ausprobieren ohne Subscription betreiben.

  - id: technical
    name: "Technik & Voraussetzungen"
    questions:
      - q: "Welche Voraussetzungen muss ein Testclient erfüllen?"
        a: |
          Unterstützt werden Windows- sowie Debian-/Ubuntu-Testclients mit mindestens **4 CPU-Kernen und 8 GB RAM**.

          Der Client muss von Checkmk überwacht werden können und sollte Internetzugang haben, damit die benötigten Python-Umgebungen automatisch aufgebaut werden können.

          Die jeweils aktuellen und verbindlichen Anforderungen stehen in der Checkmk-Dokumentation.

      - q: "Welche Tests brauchen eine entsperrte Windows-Desktop-Sitzung?"
        a: |
          Alle Tests, die die **grafische Oberfläche einer lokal installierten Anwendung** bedienen — etwa SAP GUI, Citrix-Clients oder klassische Windows-Software. Ohne angemeldete, entsperrte Benutzersitzung gibt es dort schlicht nichts zu klicken. Das ist keine Einschränkung von Robotmk, sondern eine harte technische Bedingung.

          Alles, was ohne GUI auskommt, läuft **headless** — also ganz ohne Desktop-Sitzung. Dazu gehören auch Web-Tests: Firefox, Chromium und WebKit lassen sich im Headless-Modus betreiben.

      - q: "Was ist der Unterschied zwischen Robotmk v1 (MKP) und v2 (Synthetic Monitoring)?"
        a: |
          **v1** war die Community-Erweiterung: ein MKP, das man selbst installiert und gepflegt hat. Die Python-Umgebungen auf den Testclients mussten Sie von Hand aufsetzen und aktuell halten.

          **v2** ist Synthetic Monitoring als fester Bestandteil von Checkmk. Die wesentlichen Unterschiede:

          - **Integriert statt nachinstalliert** — Konfiguration über die normale Checkmk-Regelverwaltung, kein separates MKP.
          - **Automatisches Environment-Management** über RCC: Sie beschreiben pro Suite in einer YAML-Datei, was der Test braucht; die passende Umgebung wird auf dem Client selbstständig und reproduzierbar erzeugt.
          - **Offizieller Support und Dokumentation** durch die Checkmk GmbH.
          - Deutlich robustere Ausführungssteuerung und Ergebnisverarbeitung.

          v1 wird nicht mehr weiterentwickelt.

      - q: "Wie migriere ich von Robotmk v1 auf v2?"
        a: |
          Sanft — Sie müssen nicht an einem Stichtag umstellen.

          Das v1-MKP lässt sich auf Checkmk 2.3+ parallel installieren und kommt dem integrierten v2 nicht in die Quere. Sie können also Suite für Suite umziehen, während der Rest unverändert weiterläuft.

          An den Robot-Framework-Suites selbst ist **keine Änderung** nötig. Der einzige neue Schritt: Für jede Suite schreiben Sie eine Environment-Spezifikation (YAML), damit die passende Umgebung automatisch erzeugt werden kann.

  # ── 5 ───────────────────────────────────────────────────────────────────────
  - id: learning
    name: "Einstieg & Lernen"
    questions:
      - q: "Wie viele fertige Tests bringt Synthetic Monitoring mit?"
        a: |
          **Keinen einzigen.** Diese Erwartung ist verbreitet, deshalb hier ganz deutlich:

          Robotmk bzw. Synthetic Monitoring ist die Lösung, um Ergebnisse von Robot-Framework-Tests in Checkmk zu integrieren. Das *Schreiben* dieser Tests bleibt Aufgabe des Kunden — und das ist auch richtig so, denn niemand außer Ihnen kennt Ihre Geschäftsprozesse.

          Sie stehen dabei aber nicht vor einem leeren Blatt: Das Robot-Framework-Ökosystem liefert fertige Libraries für praktisch jede Technologie, und [robotmk-starter](https://github.com/elabit/robotmk-starter) enthält CI-getestete Beispiel-Testfälle als Ausgangspunkt.

      - q: "Wie lerne ich Robot Framework und Robotmk?"
        a: |
          Es gibt inzwischen eine ganze Reihe guter Einstiege:

          - **Checkmk-Dokumentation** — die verbindliche Referenz für Synthetic Monitoring.
          - **Checkmk-YouTube-Kanal** — unter anderem „Getting Started with Synthetic Monitoring“ (Testclient aufsetzen, ersten Test schreiben) und „Integrating Robot Framework tests in Checkmk“ (Robotmk konfigurieren, Services discovern, Monitoring einrichten).
          - **Robot Framework Slack** — eine sehr hilfsbereite Community.
          - **Dieses Blog** — Tutorials, Best Practices und Neuigkeiten aus der Praxis.
          - **[robotmk-starter](https://github.com/elabit/robotmk-starter)** — CI-getestete Boilerplate-Testfälle zum Abschauen.
          - **Robotmk Academy** — mein Online-Kurs, zugeschnitten auf Synthetic Monitoring mit Robot Framework und Checkmk. Er bereitet zugleich auf die RFCP-Prüfung (Robot Framework Certified Professional) vor. Details finden Sie unter [Services](/de/services/).

      - q: "Gibt es eine Aufnahmefunktion für Tests („click and point“)?"
        a: |
          Nein — und das ist eine bewusste Entscheidung, keine fehlende Funktion.

          Hinter der Frage steckt meist die Sorge vor dem „Programmieren“. Klare Antwort: Robot Framework hat keine grafische Test-Oberfläche, hier schreiben Sie tatsächlich Code. Dank der Keyword-Syntax ist dieser Code aber außergewöhnlich gut lesbar — genau dafür wurde Robot Framework überhaupt erfunden.

          Warum keine Aufnahme? Jeder Test besteht aus drei Dingen:

          - der **Test-Logik** (was getan werden muss),
          - der **Test-Technik** (wie es getan wird),
          - den **Testdaten** (womit getestet wird).

          Ein Recorder wirft alle drei in einen Topf. Das sieht auf den ersten Blick gut aus, skaliert aber nicht: Für jeden ähnlichen Test müssen Sie erneut aufnehmen, und sobald sich Anwendung, Logik, Technik oder Testdaten ändern, nehmen Sie alle betroffenen Tests von vorn auf. Die Menge an Code wächst schnell ins Unübersichtliche.

          Robot-Framework-Code lässt sich stattdessen in Schichten schreiben: Die oberste Keyword-Ebene beschreibt nur die Logik („WAS wird getestet?“), die Ebene darunter die Teilschritte mit den Testdaten, die unterste die technische Umsetzung. Ändert sich etwas, fassen Sie genau eine Schicht an.

          Ein Vergleich aus der HiFi-Welt: Robot Framework ist eine Anlage aus einzelnen Komponenten, die je eine Aufgabe erfüllen — Quelle, Verstärker, Lautsprecher. Jede lässt sich reparieren, ersetzen und modernisieren; solche Anlagen halten praktisch ewig. Test-Recorder sind Kompaktanlagen: auf den ersten Blick praktisch, aber kaum zu reparieren, weil alles fest in einem Gehäuse verbaut ist.
```

// Category pills + live search for the FAQ page.
//
// Progressive enhancement over a page that already works: the markup ships a
// plain, grouped list of native <details> accordions, and the control bar is
// server-rendered with `hidden`. This module is what un-hides it — so if the
// bundle fails to load, the visitor never sees controls that do nothing.

export function init() {
  const controls = document.querySelector('[data-faq-controls]');
  if (!controls) return;

  const list = document.querySelector('.faq__list');
  const input = document.getElementById('faq-search');
  const noResults = document.querySelector('[data-faq-no-results]');
  if (!list || !input || !noResults) return;

  const pills = Array.from(controls.querySelectorAll('.faq__pill'));
  const groups = Array.from(list.querySelectorAll('.faq__category'));

  // Fold case and strip diacritics, so "Ausfuhrung" finds "Ausführung".
  const normalise = (s) =>
    s.toLowerCase().normalize('NFD').replace(/[\u0300-\u036f]/g, '')

  // Question and answer text are searched together, indexed once up front.
  const items = Array.from(list.querySelectorAll('.faq__item')).map((el) => ({
    el,
    haystack: normalise(el.textContent),
  }));

  let category = 'all';
  let query = '';

  function apply() {
    let totalVisible = 0;

    groups.forEach((group) => {
      const inCategory = category === 'all' || group.dataset.category === category;
      let groupVisible = 0;

      items
        .filter(({ el }) => group.contains(el))
        .forEach(({ el, haystack }) => {
          const show = inCategory && (query === '' || haystack.includes(query));
          el.hidden = !show;
          // Collapse anything being filtered away, so it isn't left open
          // when it comes back into view.
          if (!show) el.open = false;
          if (show) groupVisible += 1;
        });

      group.hidden = groupVisible === 0;
      totalVisible += groupVisible;
    });

    noResults.hidden = totalVisible > 0;
  }

  pills.forEach((pill) => {
    pill.addEventListener('click', () => {
      pills.forEach((p) => p.classList.remove('faq__pill--active'));
      pill.classList.add('faq__pill--active');
      category = pill.dataset.category;
      apply();
    });
  });

  input.addEventListener('input', () => {
    query = normalise(input.value.trim());
    apply();
  });

  // Deep link like /de/faq/#licensing preselects that category.
  const hash = window.location.hash.slice(1);
  const hashPill = hash && pills.find((p) => p.dataset.category === hash);
  if (hashPill) hashPill.click();

  controls.hidden = false;
}
```
